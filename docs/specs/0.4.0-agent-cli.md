# 0.4.0 spec: coding-agent CLIs as providers, and `evalproof init`

Status: approved for implementation (2026-11-13). Research behind every flag below:
`/tmp/evalproof-agentcli/LOCAL.md` (local runs, claude 2.1.322, codex 0.167.2) and
`/tmp/evalproof-agentcli/WEB.md` (docs, terms, prior art). Read the relevant section before
changing a flag.

## Goal

A team that already has Claude Code or Codex logged in can add evalproof to a repo with one
command and run the judge (or the system under test) on that login, with no API key:

```bash
uvx evalproof init          # writes evals/, a CI workflow and an agent skill
uvx evalproof run evals/suite.yaml
```

## Part A: `claude-code` and `codex` providers (stable)

### Targets

- `claude-code:<model>`: `<model>` is passed to `--model` (aliases `haiku`, `sonnet`, `opus`,
  or a full id).
- `codex:<model>`: `<model>` is passed to `-m` (e.g. `gpt-6-luna`).

Register both in `providers/__init__.py` (`make_provider`, `LLM_PROVIDERS`). They must work
anywhere a `TargetConfig` is accepted (judge and system).

### New module `src/evalproof/providers/agent_cli.py`

A base class `AgentCLIProvider` holding what all CLI providers share, plus one subclass per
CLI. It satisfies the existing `Provider` protocol (`name`, `model`, `chat`).

Shared behaviour, each call:

1. **Binary**: `shutil.which(<binary>)`. Missing: `ProviderError` with the install command
   (`npm install -g @anthropic-ai/claude-code`, `npm install -g @openai/codex`).
2. **Working dir**: a fresh `tempfile.mkdtemp(prefix="evalproof-")`, used as `cwd` and removed
   afterwards (also on error). Never run in the user's project dir: project `CLAUDE.md`,
   `AGENTS.md` and rules leak into the prompt otherwise (verified canary leak).
3. **Prompt on stdin**, not argv (no `ARG_MAX` limit, prompt text not visible in `ps`). Claude:
   `-p` with no prompt arg reads stdin (verified). Codex: prompt arg `-` reads stdin (verified).
   Stdin is the prompt bytes then EOF; never leave stdin an open pipe (claude stalls 3 s).
4. **Messages to prompt**: `split_system(messages)`. The system text goes to a file in the temp
   dir and is passed by path (claude `--system-prompt-file`, codex
   `-c model_instructions_file=<path>`). If there is no system message, write a one-line
   neutral system prompt ("You are a careful assistant. Answer the user's message.") so the
   CLI's agent prompt is always replaced. A single user message is sent as is. Several turns
   are rendered as a transcript: `User: ...` / `Assistant: ...` blocks separated by blank
   lines, ending with the last user turn.
5. **Environment**: copy `os.environ`, then remove the API-key variables listed per CLI below,
   so the CLI uses the subscription login. If `TargetConfig.api_key_env` is set, read that
   variable (error if unset) and set it under the CLI's key name instead. Never read, copy or
   log OAuth token files or keychain entries. Variables like `CLAUDE_CODE_OAUTH_TOKEN` are left
   alone (that is how CI uses a subscription token).
6. **Process**: `subprocess.run(..., stdin=<prompt>, capture_output=True,
   timeout=cfg.timeout_s, start_new_session=True)`. On timeout kill the whole process group
   (`os.killpg`) and raise `ProviderError("... timed out after Ns")`. Non-zero exit or an error
   in the output: `ProviderError` carrying the CLI's own message, truncated to 500 chars.
   Never include the environment in an error.
7. **Retries**: only for errors that are clearly transient (claude `api_error_status` in
   429, 500, 502, 503, 529; codex error text containing "rate limit" or "overloaded"), via the
   existing `with_retries`. Timeouts and auth errors are not retried.
8. **Latency**: wall time of the subprocess in ms.
9. **Version**: `<binary> --version`, run once per binary path per process (`functools.cache`),
   stored as the raw first line, e.g. `2.1.322 (Claude Code)`, `codex-cli 0.167.2`.
10. **No permission-bypass flags, ever** (`--dangerously-skip-permissions`, `--yolo`,
    `--full-auto`, `danger-full-access`). Tools are switched off instead.

Generation params: the CLIs expose no temperature, seed or max-tokens control (verified for
both). `temperature`, `seed` and `max_tokens` are ignored. `think` maps to codex reasoning
effort: `think: false` gives `-c model_reasoning_effort=low`, `true` gives `medium`;
`params.extra["reasoning_effort"]` overrides it (codex only, validated against
`low|medium|high|xhigh|max`). Claude ignores `think`. No other `extra` keys are passed through:
arbitrary CLI arguments could undo the isolation.

### Claude Code subclass

Command (verified isolation: 0 tools, 0 MCP servers, 0 skills, canary `NONE`, ~0.7k prompt
tokens, median 1.43 s on haiku):

```
claude -p --output-format json --no-session-persistence --model <model>
       --setting-sources "" --tools "" --strict-mcp-config --disable-slash-commands
       --system-prompt-file <tmp>/system.txt
```

plus env `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. Do not use `--bare` (needs an API key).
Removed key variables: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`. With `api_key_env` set, the
value goes into `ANTHROPIC_API_KEY`.

Output: stdout is a JSON array of events. Take the element with `type == "result"`
(no such element: `ProviderError` with stderr).
- error if `is_error` is true (do not trust `subtype`, it stays `"success"` on errors); message
  is `result`, status is `api_error_status`.
- text: `result`.
- tokens in: `usage.input_tokens + usage.cache_creation_input_tokens +
  usage.cache_read_input_tokens`; tokens out: `usage.output_tokens`.
- model: the `modelUsage` key with the most output tokens (the resolved id, e.g.
  `claude-haiku-5-5`); fall back to the requested model.
- also accept a single JSON object (older versions printed one object, not an array).

Exact sample outputs, including the bad-model error, are in LOCAL.md section 1.3 and 1.8;
copy them into test fixtures.

### Codex subclass

Command (verified isolation: canary `NONE`, shell off, median 4.06 s on gpt-6-luna):

```
codex exec --json --ephemeral --skip-git-repo-check -s read-only
      --ignore-user-config --ignore-rules -m <model>
      -c model_reasoning_effort=<low|...> -c project_doc_max_bytes=0
      -c model_instructions_file=<tmp>/system.txt
      --disable shell_tool --disable plugins --disable apps --disable hooks
      --disable multi_agent -
```

Also check `codex features list` for a feature that removes the skills block (~9.6k tokens,
LOCAL.md 2.5). If one exists, add `--disable <it>` and confirm the drop with the zero-cost
render `codex <same -c/--disable flags> debug prompt-input "Q"` (global flags go before the
subcommand; `--ignore-user-config` and `--ignore-rules` are `exec`-only). Do not make real
model calls to check this.

Removed key variables: `OPENAI_API_KEY`, `CODEX_API_KEY`. With `api_key_env` set, the value
goes into `CODEX_API_KEY`.

Output: JSONL, one event per line; skip lines that are not JSON (stderr noise is on stderr,
but be lenient).
- error if any event has `type` `turn.failed` or `error`, or exit is non-zero; message from
  `error.message` / `message`.
- text: the last `item.completed` whose `item.type == "agent_message"`.
- tokens in: `turn.completed.usage.input_tokens` (already includes the cached part); out:
  `usage.output_tokens`.
- model: Codex does not report one; use the requested model.
- an `item.completed` of type `command_execution` means a tool ran: raise `ProviderError`
  ("codex ran a tool; isolation broken"). It should never happen with `shell_tool` disabled.

### Fingerprint, cache key and the gate

Each `AgentCLIProvider` exposes:

- `fingerprint() -> dict[str, str]`: `cli` (`claude-code` / `codex`), `cli_version`,
  `isolation` (a constant per subclass, e.g. `claude-code/1`; bump it whenever the flag set
  changes), `sampling` (`cli-default`).
- `cache_salt(params)`: returns `fingerprint()` plus the codex reasoning effort. This makes a
  CLI upgrade or a flag change a cache miss, through the existing hook in `cache.py`.

`runner.environment()` records, for every target and not only CLI ones:

- `judge_target` (the judge's `target` string) and `system_target` when the system is an LLM
  target.
- for CLI targets, the fingerprint keys prefixed with the role: `judge_cli`,
  `judge_cli_version`, `judge_isolation`, `system_cli`, ... Version lookup must not make a
  model call.
- `judge_model_resolved`: the sorted, comma-joined set of `ChatResponse.model` values the judge
  returned during the run (cached responses included). Collect it with a thin recorder around
  the judge; set it when the run finishes. Same for `system_model_resolved` if it is simple to
  do; skip it if it is not and say so.

`compare` adds `same_judge: bool` and `judge_changes: list[str]` (e.g.
`"judge_cli_version: 2.1.322 (Claude Code) -> 2.1.400 (Claude Code)"`). Compare only the keys
`judge_target`, `judge_cli`, `judge_cli_version`, `judge_isolation`, `judge_model_resolved`,
and only a key present in both runs, so runs written by 0.3.0 still compare as before.

`gate.decide`: if `not cmp.same_judge`, fail with `EXIT_CANNOT_GATE` and list the changes,
unless the gate allows it. Add `allow_judge_change: bool = False` to `GateConfig` and a CLI flag
`--allow-judge-change` on `compare`. Show judge changes in the markdown report. A changed
system target or system CLI version is a warning only (that is usually the change under test).

### `evalproof doctor` (new subcommand)

`evalproof doctor [suite.yaml]`: for each target in the suite (or claude-code and codex when no
suite is given) print the binary path, version, auth mode and the isolation flag set.
Zero cost: no model call. Auth mode from `claude auth status` (JSON; print only `authMethod`,
`apiProvider`, `subscriptionType`) and `codex login status` (print its one line). Mention when
an API-key variable is set that the provider will strip. Exit 0 if every target is usable,
1 otherwise.

### Docs (Part A)

- README: a section "Use your Claude Code or Codex login" near the provider list. Cover the
  targets, `doctor`, isolation (what is turned off and why), no temperature/seed control
  (score repeat runs or calibrate the judge; check what the README already says about
  repeats and point to it), latency (claude ~1.4 s, codex ~4 s per call; set `concurrency`),
  cost (the subscription quota; no API bill), and the terms note below.
- Terms note, plain and short: OpenAI documents Codex CLI use on a ChatGPT plan, including
  automation. Anthropic's terms allow a user to run the unmodified Claude Code binary on their
  own subscription; its plan limits assume ordinary individual use, and it forbids third-party
  products from routing other users' requests through subscription credentials. evalproof
  never touches credentials: it runs your own `claude` binary, on your machine, for your own
  evals. For CI or team-wide use, use an API key (`api_key_env`). Link
  `https://code.claude.com/docs/en/legal-and-compliance`. Opt-in: nothing uses a CLI unless the
  suite names a `claude-code:` or `codex:` target.
- `docs/adr/0004-agent-clis-as-providers.md` in the style of the other ADRs: decision,
  isolation as a requirement, fingerprint gate, rejected options (SDKs: an API key is needed;
  `--bare`: needs a key; reading CLI tokens: never).
- `CHANGELOG.md`: an `Unreleased` section (Added / Changed). The new judge check is a Changed
  entry: it can turn a 0.3.0-style pass into exit 4 when the judge changed.

### Tests (Part A)

No real CLI calls in the test suite. Use fake binaries: a small Python script written into
`tmp_path/bin`, made executable, placed first on `PATH` via `monkeypatch`. It writes its argv,
cwd, stdin and the relevant env vars to a JSON file next to it, then prints a canned output
taken from LOCAL.md. Cover at least:

- command line for both CLIs (exact flags; no bypass flag; prompt not in argv);
- cwd is a fresh temp dir and is removed afterwards, also after an error;
- key variables stripped by default; `api_key_env` maps to the CLI's key name;
- system message goes to the file; multi-turn transcript rendering;
- parsing: claude array, claude single object, claude `is_error` with `subtype: success`,
  codex JSONL with noise lines, codex `turn.failed`, codex `command_execution`;
- timeout kills the process (fake binary sleeps) and raises `ProviderError`;
- missing binary message;
- retries on 529 but not on a model-not-found error;
- `cache_salt` changes when the fake `--version` output changes;
- environment keys, `judge_model_resolved`, compare `same_judge`, gate exit 4 and
  `--allow-judge-change`; old runs without the keys still gate as before;
- `doctor` output with fake binaries.

Add an opt-in live test module skipped unless `EVALPROOF_LIVE=1`; it makes one tiny call per
installed CLI. Do not run it yourself; the reviewer will.

## Part B: `evalproof init` (stable)

`evalproof init [--dir PATH] [--judge TARGET] [--ci keyless|api-key|none] [--no-skill]
[--force]`. Look at greenproof's `_cmd_init` (`~/personal_projects/greenproof/src/greenproof/cli.py:126`)
for tone and output style. Templates live as package data under `src/evalproof/templates/`
(check that the wheel includes them).

Behaviour:

- Never overwrites an existing file unless `--force`. Prints one line per file: `wrote` or
  `kept (exists)`. Exit 0. Writes nothing outside `--dir` (default: cwd).
- Judge choice when `--judge` is not given, by what is on `PATH`: `claude` gives
  `claude-code:haiku`; else `codex` gives `codex:<model>` (best effort from the zero-cost
  `codex debug models`; a placeholder with a comment if that fails); else `ollama` gives an
  `ollama:` target; else an `anthropic:` target with `api_key_env: ANTHROPIC_API_KEY`. Print
  which one was picked and why.

Files written:

1. `evals/suite.yaml`: a small working suite. The system under test is an LLM target on the
   same provider as the judge, with a system prompt, so `evalproof run` works straight away.
   Comments show how to point the system at the project's own code (follow the examples in
   `examples/`). One deterministic scorer and one `llm_judge` scorer with a short rubric. A gate
   on the judge metric.
2. `evals/cases.jsonl`: three short sample cases in the format the examples use.
3. `evals/README.md`: five lines: run, commit the run file, what CI does.
4. CI workflow `.github/workflows/evalproof.yml`:
   - `keyless` (default): evals run on a developer's machine on their own login; the PR commits
     the run file `evals/runs/latest.json` (say in `evals/README.md` which command writes it).
     CI makes no model calls: it takes the baseline from the base branch
     (`git show origin/$BASE:evals/runs/latest.json`), the candidate from the PR, and runs
     `compare --gate` (use the repo's own composite action, `action.yml`, at the 0.4.0 tag).
     If the base branch has no run file yet, pass with a notice. If the PR changes files under
     `evals/` or the system prompt but not `latest.json`, print a warning that the run file is
     stale.
   - `api-key`: CI runs the suite itself with a repository secret, then compares to the base
     branch run file. If the judge is a CLI target, install that CLI pinned to the version
     found at `init` time (pinning keeps the judge fingerprint equal, otherwise the gate exits
     4) and map the secret through `api_key_env`.
   - `none`: no workflow.
   Validate the generated YAML parses; test both variants.
5. Agent skill, the same file in two places (copies, not symlinks, for Windows):
   `.agents/skills/evalproof/SKILL.md` (read by Codex, Cursor, Copilot, OpenCode) and
   `.claude/skills/evalproof/SKILL.md` (Claude Code; also read by Cursor, Copilot, OpenCode).
   Frontmatter: `name: evalproof`, `description:` one sentence that says when to use it
   (changing a prompt, model or retrieval; checking an LLM change for regressions). Body,
   under 120 lines: how to run the suite, read the result, add a case, and gate; exit codes;
   rules for the agent: never edit `evals/runs/latest.json` by hand, never weaken a gate or
   delete cases to make it pass, report exit 1/3/4 to the human instead of working around it.
   Skipped with `--no-skill`.

Tests: init into `tmp_path` for each `--ci` value; idempotence (second run keeps all files);
`--force`; the judge choice with fake binaries on `PATH`; the written suite loads with the
real config loader; the SKILL.md frontmatter parses and both copies are identical.

Docs: README quick-start becomes `uvx evalproof init` first. CHANGELOG entry.

## Part C: experimental providers (after Part A is merged)

Same base class. Each prints one warning per process on first use:
`evalproof: <name> provider is experimental`. README lists them under "Experimental" with what
was and was not verified.

- `opencode:<provider/model>`: env `OPENCODE_CONFIG_CONTENT=<judge agent JSON, tools
  {"*": false}, permission {"*": "deny"}>`, `OPENCODE_CONFIG_DIR=<empty temp dir>`,
  `OPENCODE_DISABLE_PROJECT_CONFIG=1`, `OPENCODE_DISABLE_CLAUDE_CODE=1`; command
  `opencode run --standalone --archived --format json --agent judge -m <provider/model>`.
  Verified with a local ollama model only. Read LOCAL.md's OpenCode section for the output
  format and the system-prompt mechanism. Note in the README that archived sessions accumulate
  in OpenCode's data dir.
- `cursor:<model>`: `cursor-agent -p --output-format json --mode ask --trust --model <model>
  --workspace <empty temp dir>`. Not verified (no login on the test machine); the parser must
  be lenient and fail with a clear message on an unexpected shape. Cursor reads
  `.cursor/rules`, `AGENTS.md` and `CLAUDE.md` from the workspace; the empty workspace is the
  only isolation. Key variable `CURSOR_API_KEY`.
- `copilot:<model>`: `copilot -p <stdin or arg> -s --no-auto-update --no-ask-user --model
  <model>` in an empty temp cwd, text output (the JSONL schema is undocumented). Tokens are
  unknown (0). Not verified (not installed). Key variable `COPILOT_GITHUB_TOKEN` (a
  fine-grained PAT with "Copilot Requests"). Tool restriction: use the most restrictive
  documented option from WEB.md section 4; say in the README that isolation is unverified.

Tests: fake binaries as in Part A.

## Rules for implementers

- Work only in your worktree and branch. Commit there; do not push, tag, release or merge.
- Commit messages: no `Co-Authored-By` or any attribution trailer.
- Never touch `examples/support-qa/human-review/` (untracked user work).
- Never edit anything under `~/.claude`, `~/.codex`, `~/.cursor`, `~/.config/opencode`.
- No real model calls through any CLI. Zero-cost commands (`--version`, `--help`,
  `auth status`, `login status`, `codex debug prompt-input`, `codex debug models`,
  `codex features list`) are fine.
- Gate before reporting: `uv run ruff check`, `uv run ruff format --check`, `uv run mypy src`,
  `uv run python -m pytest -q` all clean; coverage not lower than main.
- If a flag in this spec fails on the installed CLI, or a design point is unclear, stop and
  report; do not improvise a different isolation scheme.
- Report back after about 50 tool calls, or when done, with: files changed, test counts, gate
  output, and anything you could not do.
