# 0.5.0 spec: the developer workflow

Status: implemented on the `fix/dev-workflow-0.5` branch, not released. Source: a workflow audit of
`evalproof init --ci keyless` and `--ci api-key` as a developer would use them while changing
prompts and cases. Each section says what changed, why, and the decision a reader might want
to revisit.

## Goal

Adding a case, editing a case, reading a failure and gating a first run should each work
without the gate refusing for the wrong reason, and a green gate should mean what it says.

## A. Compare across dataset changes

- Every `CaseResult` has `case_hash`: the first 16 hex characters of the SHA-256 of the
  canonical JSON of the case (id, input, reference, tags, extra fields). The runner and the
  importers set it. Runs written before 0.5 have none.
- `compare_runs` pairs by id and hash. Same id and hash: paired. Same id, different hash:
  `edited`, excluded and listed. In one run only: added or removed, not compared.
  `Comparison.comparable` is False only when the dataset hashes differ and a run has no case
  hashes, because then unchanged cases cannot be told from edited ones. `gate.decide` exits 4
  only for that, and asks for a fresh baseline. A dataset change is otherwise a warning.
- `--limit` runs pair with a full baseline on the cases they ran.
- `judge_cli_version` is advisory (`JUDGE_WARN_KEYS`): the resolved model is what decides
  whether the instrument changed. `cli_version` is out of the agent-CLI cache key (the key
  gains `SAMPLING = "cli-default"`), so a self-updating CLI keeps its cached replies.
  Both change cache keys once.

Revisit: a baseline without hashes is a hard refusal after a dataset change. The alternative
(pair on ids and warn) was rejected because an edited case would then be compared as if it
were unchanged.

## B. `evalproof verify`

- `RunInfo.suite_hash` is `config.suite_fingerprint(cfg)`: SHA-256 (16 hex) of the canonical
  JSON of the system and judge identity (target, system prompt, prompt template, params,
  base_url), every scorer's configuration and the seed. `label`, `timeout_s`, `headers`,
  `api_key_env` and `pricing` are left out: they name or pace the run, not change its answers.
- `evalproof verify RUN SUITE [--markdown FILE]` checks the suite fingerprint and that the run
  covers exactly the dataset's cases by id and hash, listing up to ten ids per problem. Exit 0
  on a match, 4 on a mismatch, 2 on a usage error. No model call.
- The composite action runs it before comparing when a suite is given and `verify-candidate`
  is `"true"` (the default); a mismatch writes `exit-code` and fails with exit 4.
- It cannot prove that scores were not edited by hand. The keyless workflow header says so.

Revisit: a run without `suite_hash` (written before 0.5, or imported) fails verify. The
message says to run the suite again.

## C. Checks that need no baseline

- `gate.min_pass_rate` (a float, or a dict by scorer), `gate.must_pass` (a list of case tags)
  and `gate.max_new_failures` (an integer). Errored cases count as failures.
- `max_new_failures` is the most cases that may go from pass to fail on a pass/fail gated
  metric, whatever the p-value; `0` suits deterministic scorers. On 30 cases, 5 regressions
  give p = 0.0625, which the significance test alone passes.
- `decide(cmp, gate, candidate=None)` applies them. With absolute checks set and no
  candidate it exits 4 rather than pass without checking.
- `run --gate` applies `min_pass_rate` and `must_pass` to the run alone (usage error when
  the suite sets neither, checked before any case runs). `compare` gains `--min-pass-rate`,
  `--must-pass` and `--max-new-failures`.
- An unknown `--metric` is a usage error (exit 2) listing the scorers. A metric that exists
  but has no paired scores stays exit 4.
- `run` writes the file, prints the report and exits 2 when every case errored, naming the
  first error. `--out` is checked for writability before any case runs. An unexpected
  exception prints one line (`EVALPROOF_DEBUG=1` re-raises); Ctrl-C exits 130.

On a continuous gated metric a scored case neither passes nor fails a `must_pass` check
(only an error or an undecided score fails it), and the gate warns that `must_pass` checked no
more than that. `min_pass_rate` on a metric with only continuous scores cannot gate (exit 4,
naming the fix); `max_new_failures` on one warns that it was not checked. A must-pass tag
that matches no case warns instead of failing.

## D. Reading a result

- Suites are strict: `extra="forbid"` on every config model. A typo fails with
  `<path>: gate.max_drops: unknown key (did you mean 'max_drop'?)`, or the valid keys.
  Validation errors no longer print pydantic's URLs.
- `run_markdown(run, max_cases=10)` ends with "Failed cases": errored, failed or undecided
  cases with the failing scorers and the error or first reason, clipped to 120 characters.
  `run --show N` and `report --show N`; 0 hides it.
- `comparison_markdown` lists regressed ids for every compared metric (ten per metric). With
  `runs=(baseline, candidate)` and `show=N` (`compare --show N`, default 5) it adds a
  `<details>` block for up to N regressed cases of the gated metrics: both outputs clipped to
  400 characters, in a code fence longer than any fence inside the text, and the candidate's
  reason. Exit 4 renders "cannot gate", not "fail".
- `run --system-prompt-file F` without `--label` labels the run `<system label or target> +
  <file name>`, so two prompt files are told apart in reports. (A `python:` target ignores
  labels, which is older behaviour.)
- `import --quiet` keeps the report off stdout; `--markdown` still writes it.

## E. Cost reported by the CLI

- `ChatResponse.cost_usd` is the cost a provider reports. The `claude-code` parser reads
  `total_cost_usd` (a number >= 0). `response_cost(resp, pricing)` uses it when the target's
  pricing is all zero and falls back to the token price otherwise.
- A cached hit returns the original call's cost, as it already did for tokens and latency.
- `LLMJudge` takes the judge's `pricing` and adds every call, retries included, to
  `judge_cost_usd`. Before this the judge's cost was not computed from pricing, so a judge
  with prices now counts toward `max_cost_usd`.
- Under a subscription login the figure is the CLI's API-equivalent estimate, not a bill.

## F. `--ci api-key` workflow

- No `paths:` filter. The workflow starts on every pull request, and a first step compares
  with the base branch over `WATCH` (default `evals/`, run files excluded). Nothing watched
  changed: a notice, and the remaining steps are skipped.
- Pull requests from forks (`head.repo.full_name != github.repository`) skip the install,
  cache, run and gate steps with a notice that forks get no secrets.
- `actions/cache` (pinned by commit SHA) stores `evals/.evalproof/cache` under
  `evalproof-${{ hashFiles('evals/**') }}`, restoring from the `evalproof-` prefix. Restore and save are separate
  steps (`actions/cache/restore`, `actions/cache/save`); the save runs right after the suite,
  before the gate, so a pull request that fails the gate keeps the answers it paid for, and is
  skipped on an exact cache hit.

## Breaking changes

- Unknown keys in a suite are errors.
- `run` exits 2 when every case errored (it wrote the file first).
- Agent-CLI cache keys change once (no CLI version, `SAMPLING` added).
- `compare --metric NAME` exits 2 when no run has a scorer called NAME.
- `compare` no longer exits 4 for a dataset change between runs that both carry case hashes.

## Not done

- Pairing of an edited case by a stable id of its own (an edit is excluded until the baseline
  is refreshed).
